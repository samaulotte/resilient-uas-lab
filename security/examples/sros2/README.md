# SROS2 example policy for the planned ROS 2 adapter

The adapter catalog lists a `ros2` adapter with status `planned`: a generic adapter for
ROS 2 robots built on lifecycle nodes and SROS2 security enclaves. No code in release
0.2.0 implements it or reads the files in this directory. They are here so that the
access boundary a ROS 2 runner should respect is written down before the adapter is,
and so that adapter authors start from a least-privilege policy instead of an open
graph.

## What the policy expresses

`reslab-runner.policy.xml` is an SROS2 access-control policy (schema version 0.2.0,
the format consumed by `ros2 security generate_artifacts -p <policy>`). It defines one
enclave, `/reslab/runner`, with one profile for a node named `reslab_runner` in the
namespace `/reslab`. The node may:

- publish on `/reslab/fault/request` (the adapter's own topic on which it announces the
  abstract effect it is about to realize, for logging on the robot side);
- subscribe to the diagnostics and state topics it needs to derive component states:
  `/diagnostics`, `/reslab/component_state`, and the lifecycle transition events of the
  nodes it observes;
- call the lifecycle services of the nodes it is allowed to disturb (`change_state`,
  `get_state`) and nothing else.

It may not publish on any control, command or actuator topic, and it may not call any
service outside the listed lifecycle services. Fault effects on a ROS 2 target are
expected to be realized through lifecycle transitions (deactivate, cleanup, shutdown
and reactivate for `unavailable`, `restart` and `crash`) and through the target's own
degradation hooks, never by injecting into control topics.

## Using it

```bash
# On the robot or simulator side, with the ROS 2 security tooling installed:
ros2 security create_keystore keystore
ros2 security generate_artifacts -k keystore -p reslab-runner.policy.xml
```

Key material generated by these commands is deployment specific and must never be
committed. The keystore path is passed to the runner through `ROS_SECURITY_KEYSTORE`,
`ROS_SECURITY_ENABLE=true` and `ROS_SECURITY_STRATEGY=Enforce`, as described in the ROS 2
security documentation for the distribution in use.

## Adapting it

Every topic and service name here is a proposal. When the adapter exists, its
documentation will fix the names, and this policy will be updated with it. Keep the
principle when adapting: allow the minimum set of topics and services, deny by default,
and never grant publish rights on anything that commands the vehicle.
